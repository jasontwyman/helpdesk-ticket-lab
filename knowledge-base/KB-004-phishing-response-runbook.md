# KB‑004 — Reporting and handling a suspected phishing email

**Applies to:** Any reported suspicious/phishing email

**Audience:** Tier‑1 help desk with Security handoff

**Related ticket:** [HD‑007](../tickets/HD-007-phishing-escalation.md)

## First principles

1. Preserve the original message and related telemetry.
2. Do not click links, browse to URLs, or open attachments on a user endpoint.
3. Treat the report as suspicious until validated; do not declare a phish or campaign from one
   user description alone.

## Ask about user interaction immediately

Record whether the user opened the message, clicked a URL, downloaded/opened an attachment,
executed a file, entered credentials, or approved MFA, with approximate timestamps. If any
credential submission, execution, or unexpected MFA approval occurred, escalate immediately for
account/session and endpoint containment according to policy.

## Preserve complete evidence

Use the approved report-phishing tool or retain the original `.eml`/`.msg`. Collect:

* full headers, including transport path and authentication results;
* envelope sender, displayed sender, recipients, subject, timestamps, and complete body content;
* displayed link text plus normalized/defanged URL destinations obtained from message source or
  approved security tooling, never by visiting the site;
* attachment names, types, sizes, hashes, and sandbox/analysis IDs when generated by approved
  tooling—do not open attachments locally; and
* relevant screenshots only as supplemental context, not as a substitute for the original.

Headers are not the entire investigative value. Body language, URLs, attachments, user actions,
and tenant telemetry can be decisive.

## Tenant and security telemetry

Security/mail administrators should correlate message trace, message ID, campaign/cluster data,
mail-security verdicts, delivery locations, related recipients, click telemetry, endpoint/identity
alerts, and any post-delivery purge or remediation status. Record query times and results; do not
claim tenant-wide scope or cleanup without live-system evidence.

## Select proportional controls

After validation, Security may purge matched messages, block specific URLs/file hashes/sender
addresses, revoke sessions, reset/disable affected accounts, review mailbox rules/sign-ins, inspect
endpoints, or initiate takedown.

Avoid blanket domain blocking. A sender can be spoofed, a legitimate mailbox can be compromised,
or a legitimate hosting domain can contain one malicious path. Block the narrowest validated
indicator that disrupts the campaign without unnecessary business impact; use broad domain blocks
only when Security validates and approves that scope.

## If credentials were entered or MFA was approved

1. Escalate immediately and follow policy for account disable/reset.
2. Revoke active sessions/tokens and review sign-ins and MFA changes.
3. Review mailbox rules, forwarding, delegated access, and sent items.
4. Correlate endpoint and tenant telemetry for follow-on activity.
5. Record each completed containment action; do not assume a password reset alone is sufficient.

## Close and communicate

Thank the reporter, provide only validated findings, and explain any required next steps. Close a
real case only after recording Security disposition, scope, containment/remediation evidence, and
user follow-up.
